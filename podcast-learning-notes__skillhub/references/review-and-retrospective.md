# 质检与复盘

终审、修复、反馈记录和复盘模式都读取本文件。

## 终审

分三轮做，每轮只看一件事，结果分栏写入 `review/final-review.md`。混成一张清单就会边看结构边抠字句，两层都漏。

```markdown
# 终审

## 第一轮 结构

- 塔尖统摄：抽 3 节，能否挂到核心内容节的塔尖下
- 同层互斥：有无包含或交叉
- 篇幅分布：有无单节超过全文四分之一
- 可整体删除的节：

## 第二轮 逻辑与保真

- 问题骨架覆盖：
- 干净稿逐段覆盖：
- 限定词抽查（随机 10 处回对干净稿）：
- 归属三分（事实 / 嘉宾观点 / 我的推论）：
- 专名准确性：
- 时间戳来源：
- 经典 Q&A 是否只是点缀：

## 第三轮 文字

- 术语异写计数：
- 超 6 行段落数：
- H3 超 18 字数、连续三个问句：
- 标点、连续空行、表格列数：

## 判断层

- 这期改变了我什么判断（≤3 条）：
- 我自己的推断（与嘉宾观点如何区分）：

## 结论

通过 / 需要修复

## 失败项

## 必须修复
```

出现以下任一情况，最终笔记应判定为需要修复：

- 明示或暗示已经完整核对原音频。
- 未读取或未使用 `extraction/question-skeleton.md` 逐项核查覆盖。
- 遗漏问题骨架中的实质问题或对应核心回答。
- 遗漏 transcript 中成体系的核心内容，如三分类、三层框架、优先级、关键机制。
- 静默编造时间戳、缺失文字稿内容、引用或外部事实。
- 把带限定条件的说法改写成绝对说法。
- 混淆嘉宾观点、事实和 agent 推测，把 agent 的推论写成嘉宾判断。
- 加入 LLM 自己的价值评判、反方观点或未被播客支持的观点发挥。
- 未主动排查 AI 专名危险误转写，或明显专名漏改。
- 忽略已知的文字稿存疑点或低置信段落。
- 默认生成 `## 自测题`、`## 存疑与待核对` 或 `## 诚实边界声明` 三个尾部模块。
- 缺少 `## 播客核心内容`（独立 H2、不编号），或正文只有一层标题、缺少 H2 主题 + H3 判断的两层结构。
- 成稿字数与所选档位偏离超过 20% 而未写明原因。
- 产物只是泛泛摘要，不是结构化学习笔记。

## 三轮的执行顺序

顺序不能颠倒：先结构、再逻辑、最后文字。文字改完再动结构，前面的字句工作全部作废。

**第一轮 结构**：不看正文，只看标题列表。把全文缩到一页提纲来审——标题连起来读是否构成一条论述，每节是否在支撑上层。

**第二轮 逻辑**：逐节标注「结论—论据—支撑」，找跳步与断点。核对覆盖必须在这一轮完成：

1. 读取 `extraction/question-skeleton.md`，逐项检查每个实质问题的核心回答是否进入 `notes/notes.draft.md`。
2. 抽查 `source/clean-transcript.md` 或对应 chunk，确认成体系内容（三分类、三层框架、优先级、关键机制）没有漏。
3. 随机取 10 处转述回对干净稿，检查限定词（多数情况下 / 在…场景下 / 有时候 / 可能 / 不一定 / 我认为）是否还在。
4. 检查 `source/extraction-notes.md` 的专名纠错与存疑项，确认笔记没有使用未修正的错误专名。
5. 检查关键结论的时间戳是否来自 transcript/chunk，不得编造。
6. 检查是否忠实转述，没有评判、反驳或延展到播客未支持的外部观点。

**第三轮 文字**：从后往前读，专抓字句。倒读能避开内容记忆，只看表面问题。

每轮结束记录问题数。问题数骤降说明该轮已到位；三轮之后仍有小瑕疵属正常，继续改的边际收益很低。

## 修复规则

如果 `review/final-review.md` 判定为“需要修复”，先修改 `notes/notes.draft.md`，再进 Phase 6 收口；Phase 6 的自检项在成稿上再跑一遍。只要做了修复，就写 `review/repair-log.md`：

```markdown
# Repair Log

- 问题：
- 已做修改：
- 剩余风险：
```

只有修复完成后才能汇报完成。若某个问题因为源信息缺失无法修复，必须在笔记和最终回复中明确标出。

## 反馈日志

每次完整运行结束后，向 `feedback-log.md` 追加：

```markdown
## <YYYY-MM-DD> - <播客 id/标题>

- 输入路径：
- 质检失败类型：
- 已做修复：
- 需要观察的模式：
```

保持简短、事实化。它是 skill 的长期记忆，不是展示报告。

## 复盘模式

当用户要求复盘或改进 skill 本身时：

1. 读取完整 `feedback-log.md`。
2. 归类重复出现的问题类型。
3. 只有出现至少 3 次的问题才视为系统性问题。
4. 提出对 `SKILL.md` 或 reference 的具体修改建议。
5. 等用户确认后再修改 skill 文件。

不要因为单次运行失败就自动重写 skill。
