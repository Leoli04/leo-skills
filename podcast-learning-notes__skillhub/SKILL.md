# 播客学习笔记

## 总纲

本 skill 把一期 AI 访谈播客整理成“用约 1/4 时间就能 get 到嘉宾观点”的学习笔记。AI 领域前沿常无定论，嘉宾所讲是个人观点而非定论。LLM 的本分是忠实整理和转述嘉宾观点：不评判、不补充对立观点、不发挥己见。补充仅限无争议的基础概念扫盲。

对内容绝对忠实：不改原意，保留限定词，明确标注“事实 / 嘉宾观点 / 预测 / 存疑”。对呈现精心整理：结构清晰，好读，重点突出，能快速扫描，也能回到原文核对。

最终学习笔记的正文默认就是嘉宾观点的整理，不要反复写“嘉宾认为”“嘉宾说”“在嘉宾眼里”。只有内容来自 show notes、主持人、agent 基础概念补充、预测/暴论、转写存疑或来源不一致时，才显式标注来源或性质。

默认产物是 Obsidian/Notion 兼容的朴素 Markdown。只有用户明确需要时，才从 Markdown 轻量导出 PDF。不要做展示型 show notes、视觉文章、dashboard、报告、落地页或交互式 HTML。

## 架构

坚持双模型分工：

- 转写模型：音频 -> 文字稿。跑批、大量长期处理、重视免费和隐私时，推荐本地 FunASR（`scripts/transcribe_funasr.py`，优先带说话人分离）。单次/低频、希望省配置时间、可接受付费时，推荐云 ASR：通义 / DashScope、飞书等，使用 `scripts/transcribe_cloud_asr.py` 规范化结果。
- 写笔记模型：文字稿 -> 学习笔记。使用用户当前配置的 LLM/agent 环境完成。

不要把转写和写笔记焊死。如果 `source/transcript.md` 已存在，重写笔记、改风格、加深内容、重做术语表或自测题时都复用它。除非用户明确要求，或 transcript 缓存缺失/明显过期，否则不要重跑转写。

选择转写方案时先判断使用场景：

- 跑批/多期播客/长期使用：推荐本地 FunASR，一次配置后批量免费复用。
- 单次或少量播客：推荐通义/飞书等云转写服务，或用户提供已有文字稿/API 结果。
- 对专名准确率要求高：优先使用播客官方文字稿、飞书/通义等带编辑能力的文字稿，或用 show notes 辅助纠错。
- 本地 FunASR 未配置时：不要卡死；提示用户可改走云转写或直接上传文字稿。

## 输入与前置准备

支持三条输入路径，并统一汇合到 `source/transcript.md`：

- 音频 URL 或音频文件 -> 已配置 ASR -> `source/transcript.md`。
- `.md` / `.txt` 文字稿 -> 复制/规范化为 `source/transcript.md`，跳过转写。
- 小宇宙单集页 -> 运行 `scripts/download_xiaoyuzhou_episode.py`，提取音频到 `source/audio.m4a`，提取 show notes 和元数据到 `source/show-notes.md`，再按音频路径转写。

`source/show-notes.md` 只作为辅助元数据：标题、原始链接、发布时间、音频时长、节目简介、官方时间轴、嘉宾信息、正确专名线索。它不能替代 transcript，也不能覆盖 transcript 里的实际发言。若 show notes 与 transcript 冲突，标注“来源不一致”，默认以 transcript 作为事实底座。

## 工作区结构

在每期播客的工作目录里创建并使用以下结构：

```text
source/
  audio.m4a
  show-notes.md
  transcript.md               # 原始/最终采用文字稿，Phase 1 的输入
  clean-transcript.md         # Phase 1 产物：清洗后的干净稿
  extraction-notes.md         # Phase 1 产物：纠错与存疑记录，不是 Phase 1 输入
  asr/
    funasr/
      transcript.md
      raw.json
      extraction-notes.md
    tongyi/
      transcript.md
      raw.json
      extraction-notes.md
extraction/
  question-skeleton.md        # Phase 2 产物：实质问题骨架 + 必须覆盖清单
  chunk-index.md
  chunks/
    chunk-001.md
    chunk-002.md
notes/
  notes.draft.md              # Phase 4 产物：记录稿，保留全部锚点，覆盖优先
  notes.md                    # Phase 6 产物：最终文档，无锚点，呈现层已收口
  notes.带时间锚点-溯源版.md    # 可选：与 notes.md 同结构、保留锚点的回听核对副本
  notes.pdf
review/
  final-review.md
  repair-log.md
feedback-log.md
```

所有重要决策都要落盘，不能只依赖聊天上下文。若不确定某个决定是否已经确认，先回读对应文件。

## 流程

### Phase 1：全文清洗

输入是 `source/transcript.md`、`source/show-notes.md` 元数据和 `references/ai-term-corrections.md`。注意：`source/extraction-notes.md` 是本阶段产出，不是输入；不要引用一个还不存在的文件。

目标是在切块前先把整篇 transcript 洗成稳定事实底座，产出：

```text
source/clean-transcript.md
source/extraction-notes.md
```

重点修“危险专名错误”：专名被转成另一个正常词，句子读着通顺但语义全变，例如 `skill -> scale`、`agent -> AG`、`prompt -> promote`、`ChatGPT -> 拆 GPT`、`Claude -> cloud`。这类错误不容易露馅，必须用 AI 专名误转写对照表主动排查，而不是被动等待上下文暴露。

清洗规则：

- 用 show notes 的正确标题、嘉宾名、产品名、时间轴和专名线索纠正 transcript。
- 读取 `references/ai-term-corrections.md`，主动排查常见 AI 专名误转写。
- 修明显标点、断句、重复 header、坏空行和说话人切错。
- 保留时间戳和说话人标签；没有时间戳就不要编造。
- 对上下文强支持的专名错误可直接修正，并在 `source/extraction-notes.md` 记录。
- 拿不准的地方标“存疑”，不要硬改，不要臆造缺失内容。
- 保持口语事实，不做书面化改写，不消灭嘉宾表达里的限定词。

`source/extraction-notes.md` 应记录：采用的 transcript 版本、show notes 元数据、已修正专名、说话人映射、仍存疑的专名/句子/说话人切分。

### Phase 2：提问题骨架 + 切块

输入是 `source/clean-transcript.md` 和 `source/show-notes.md`。从干净稿提取主持人的实质性提问，形成“问题骨架”，同时作为后续防遗漏的“必须覆盖清单”。实质提问是切块的强信号，但不是铁律；agent 需要结合嘉宾回答的连续性、主题是否真正转换、追问是否仍服务同一问题来判断切点。

产出：

```text
extraction/question-skeleton.md
extraction/chunk-index.md
extraction/chunks/chunk-001.md
...
```

区分两类主持人发言：

- 实质提问：引出新话题、要求嘉宾解释概念/机制/判断/例子的发问。它可以作为问答单元切点。
- 附和、追问、过渡：如“对对对”“嗯”“那这样呢”“刚才说到”等，不单独作为切点，并入所在问答单元。

不要机械地“凡主持人开口就切”。这会切碎对话，也会斩断嘉宾的长回答。

切块规则：

- 优先按问答单元切块，而不是按固定字数或 show notes 每个时间戳硬切；但不要因为主持人提出了一个短追问就强行另起 chunk。
- 一块通常包含一个实质问题、必要的追问/附和、嘉宾完整回答。
- 对长回答可保留为同一 chunk，除非嘉宾明确进入新主题。
- 如果一个主题跨多个实质问题反复展开，Phase 2 可以分成多个问答 chunk；Phase 4 必须再把它们归拢到同一学习主题。
- 一块里若含两个以上独立判断（不同结论、不同前提、不同例子各自成立），在 chunk 头部标出这些「卡点」。问答块是消化单位，不是最小单位；不标出来，Phase 4 就只能整块搬运。
- `question-skeleton.md` 要列出每个实质问题、对应时间范围、所属 chunk、必须覆盖的核心内容。

### Phase 3：逐块精读

逐块读取 `extraction/chunks/*.md`，抽取嘉宾观点、论证、限定词、具体例子和专名存疑。每块文件只做抽取和标注，不写成最终笔记。

每块必须包含：

- 主持人的实质问题。
- 嘉宾的核心回答。
- 嘉宾观点与事实陈述的区分。
- 关键限定词、前提、适用范围。
- 具体例子、类比、数字、工具/公司/产品/论文名。
- 专名存疑和转写断裂。
- 可用于最终笔记或自测的问题。

有框架、分类、成体系的内容必须完整抽取。例如“memory 三分类”“Harness 三层”“模型/上下文/工具优先级”。不要因为 chunk 靠后或内容复杂就草草带过。

### Phase 4：重排整合（产出记录稿）

抛开问答顺序，按学习主题重组成 `notes/notes.draft.md`。最终笔记主体是转述形式，不是逐块拼接，也不是主持人问答实录。Phase 2 的问答切块只是消化原料的办法，不能决定最终笔记结构。

这一阶段的唯一目标是**不漏 + 归位正确**，不是好读。因此允许草稿偏长、允许小节划分不顺、允许句子书面化，也只在这一阶段保留全部时间锚点。不要在这里做标题炼句、跨节去重、体量压缩或入口导语——那是 Phase 6 的事，混在一起做必然来回返工。

写作前读取 `references/note-template.md`。合成时必须：

- 把散落在不同问答里的同主题内容归拢到同一节讲透。
- 对照 `extraction/question-skeleton.md` 的“必须覆盖清单”，确认每个实质问题对应的核心内容都进入笔记。
- 没有现成主题容器的核心内容要新开一节，不要因为不合当前结构就漏掉，例如 memory 三分类、PM 是否该懂 Harness 等。
- 只忠实转述嘉宾观点，不评判、不补充反方观点、不发挥己见。基础概念扫盲可以少量补充，但不能伪装成嘉宾原话。
- 正文默认以嘉宾观点展开，避免反复出现“嘉宾认为/嘉宾说/在嘉宾眼里”等归因套话；预测、存疑、show notes 来源、主持人观点或 agent 补充才显式标注。
- 遵循“有骨架的 prose”：解释用 prose 讲透，并列/分层/对比用结构呈现。
- 关键结论和关键定义挂 `[mm:ss]` 或 `[hh:mm:ss]` 锚点；若干净稿无时间戳，则不编造。
- 每节有可见的收束句，但不要加“学习要点”“带走点”这类标签；需要收束时直接把判断写成加粗句。
- 避免两个极端：全 bullet 的机械档案；全散文、不可扫描的文章。

**归属三分**。每段内容必须能归到三类之一，不能混着写：嘉宾原话（默认形态，不加归因套话）、主持人引导（只在影响理解时点出「主持人追问」）、**我的推论**（agent 的推断、类比、引申）。第三类最容易出问题——写进正文，读者会当成嘉宾判断。规矩是：推论要么删掉，要么用「（按：…）」就地标出，全篇不超过三处；成段的推论不进正文，写进 `review/final-review.md` 的「判断层」。

**判断层**。在 final-review 里另记三条以内：这期内容改变了我什么判断，以及哪一句是我自己的推断。它不进入笔记正文，但必须留痕——否则半年后无法区分「他说的」和「我当时推的」。

末尾另设可选的“经典 Q&A”模块：精选 2-4 段最有代表性、例子最生动的问答，以对话原貌保留主持人问 + 嘉宾答。它是最后的点缀，不影响前面按学习逻辑重排的主体。不要把整篇笔记写成 Q&A。

### Phase 5：三轮审校

终审时读取 `references/review-and-retrospective.md`，结果写入 `review/final-review.md`。

审校必须分三轮、每轮只看一件事。混在一轮做必然漏检——一边核覆盖一边抠字句，两层都会漏。三轮顺序不能颠倒：先改结构，再补论证，最后动字句；顺序反了，前面的字句工作全部作废。

**第一轮 结构**（只看提纲，把全文缩成一页标题来审）

- 每节能否挂到核心内容节的塔尖下；挂不上的节删掉，或说明塔尖写窄了。
- 同层标题是否互斥，有无包含或交叉（「性能优化」与「索引优化」并列即错）。
- 篇幅是否失衡，有无单节超过全文四分之一。
- 有无可整体删除的节：信息量明显低于同类节的，优先砍它。

**第二轮 逻辑与保真**（逐节标「结论—论据—支撑」，找断点）

- 用 `extraction/question-skeleton.md` 逐项核查：每个实质问题、每段核心回答是否已进入 `notes/notes.draft.md`。
- 用 `source/clean-transcript.md` 逐段对照查遗漏，发现漏掉成体系内容先补回笔记。
- 限定词抽查：随机取 10 处转述回对干净稿，检查「多数情况下 / 在…场景下 / 有时候 / 可能 / 不一定 / 我认为」是否还在。删掉限定词，等于把谨慎判断改成绝对结论，这是最难自查的一类失真。
- 事实 / 嘉宾观点 / 我的推论三类是否分清；有无把推论写成嘉宾判断。
- 专名是否漏改，尤其是正常词形的危险误转写。
- 关键结论时间戳是否来自干净稿，不得编造。
- 「经典 Q&A」是否只是点缀，未替代主体。

**第三轮 文字**（从后往前读，避开内容记忆）

- 术语一致：同一概念全文一个写法，异写计数为 0（见 Phase 6 术语锚定）。
- 段落颗粒度：一段一意；段首句是主张句，不是铺垫句；单段不超过约 6 行。
- 长句断句：一句里出现三个以上「的」，或两个以上逗号分句，拆开。
- 标点、重复标点、连续空行、表格列数。

收敛判据：每轮记下问题数，问题数骤降说明该轮已到位；三轮之后仍有小瑕疵属正常，继续改的边际收益很低。

如果质检发现 fail 项，先修复 `notes/notes.draft.md`，再汇报。只要做了修复，就写 `review/repair-log.md`。“只汇报不修复”不符合本 skill。

### Phase 6：成稿收口

输入 `notes/notes.draft.md`，产出 `notes/notes.md`。这一阶段只做**好读**，与 Phase 4 的“不漏”方向相反，因此必须单独走一遍。在同一遍里同时做加法和减法，是反复改稿的根因。

**先定体量档位，再动笔。** 没有预设目标，压缩就会停在「看着差不多」的地方，改多少轮也落不到承诺值。

| 档位 | 汉字量 | 适用 |
| --- | --- | --- |
| 速读 | 3000–4000 | 只留判断链，供事后检索 |
| 标准 | 5000–6500 | 默认；论证保留、细节压缩 |
| 完整 | 8000–10000 | 框架类内容多，需保留推导过程 |

档位在 Phase 4 动笔前就该定，因为它决定素材取舍；到 Phase 6 才定，剩下的手段只有删。成稿字数与档位偏差超过 20%，必须在 `review/final-review.md` 写明原因，不许沉默交付。

然后七件事，按顺序做：

1. **立塔尖**。写一句话主旨放进核心内容节首段。判据不是句子漂亮，而是**随机抽任意一节，能否挂到它下面**。挂不上的节，要么塔尖写窄了，要么该节不该留在正文。
2. **定 H1**。用「主题 + 核心判断」，如 `# 量化宏观配置：用结构换稳定`，不要用播客原始标题。原标题下放到元数据，溯源不丢。
3. **设核心内容节**。顺序为 H1 → 元数据 → `## 播客核心内容`（独立 H2、**不编号**）→ 正文一到 N。这一节含 2 段（处境 / 答案）+ 一张不超过 5 行的取舍对照表，3 分钟可走完。概要节不编号的理由：它是摘要，不是第 1 个主题，编号会让读者以为正文有 N+1 个主题。
4. **去重与压缩**。先查跨节重复长句（同一判断在正文与 Q&A 各出现一遍是最常见形态），清零后再压体量。压缩用三刀，别逐句瘦身——逐句改只降个位数百分比，还留下一堆被磨平的论证。

   - 第一刀删形容词与程度副词：「非常」「极其」「显著的」「大幅的」多数可删而不损信息，它们表达的是强调意图，不是事实。
   - 第二刀删重复：同一判断只留最有力的一处。开头提出、每节末尾再复述一遍，是最常见的冗余。
   - 第三刀删铺垫：「在开始之前需要说明的是」「众所周知」这类句子，删掉读者不会感到任何信息缺失。

   删完统计删除率：低于 10% 说明只做了编辑、没做删减；高于 30% 说明删到论据了。
5. **术语锚定**。从正文挑 5–8 个核心术语，各定唯一写法，列进 `review/final-review.md`；再全文检索异写，计数必须为 0。三类高发：同音词（风险平价 / 风险评价）、简称全称混用（波动贡献 / 波动性贡献）、译名不统一。这一步放在改字句之前，否则改完还要再查一遍。
6. **分级标题**。H2 记主题（可检索、不下结论），H3 才可用判断句，且判断必须是嘉宾的，不是 agent 加的评语。判据：把标题单独抄出来读，应像一句结论或一个真问题。H3 不超过 18 字；同层标题字数大致相当（极差不超过 2 倍）；不连续排三个问句。出现「一页读懂」「一张表」「一条线」「带走点」「三个性质」「本文分为几部分」这类描述文档结构的词，一律改掉。
7. **删锚点**。锚点是核对工具，不是阅读内容，寿命到 Phase 5 结束。删除前先存一份同结构副本 `notes/notes.带时间锚点-溯源版.md`，供日后回听或被质疑时核对；`notes.md` 本身不留任何 `[mm:ss]`。

删锚点时有两个已踩过的坑：正则用 `[ \t]*` 而非 `\s*`（`\s` 含换行，会吃掉段落边界，把 `### 标题` 降级成正文）；清理“标点前空格”时不要用 `\u3000-\u303f` 这类宽区间，`「` 属 CJK 标点区，会把 `### 「…」` 里 `###` 后的空格删掉，同样毁掉标题。删完必须复查 H2/H3 计数与删前一致——这是唯一能发现结构性降级的信号，肉眼看不出来。

正文不许出现制作说明：转写来源、是否核对过原音频、本文分几部分、下面这张表、本节带走点。溯源写 `source/extraction-notes.md`，评审结论写 `review/final-review.md`。

成稿自检（结果追加到 `review/final-review.md` 末尾）：

- 锚点数 = 0；跨节重复长句 = 0；H2/H3 计数与 draft 一致
- 每张表格列数一致；无连续空行；无行尾双空格
- 单段 ≤ 260 全角字符（约 6 行），超出的已拆
- 术语异写计数 = 0；字数落在档位区间内，或已写明偏差原因
- 随机抽 3 节，能否挂到塔尖下
- 全文搜「一页读懂 / 一张表 / 一条线 / 带走点 / 本文 / 下面这张表 / 基于转写稿」，命中即 fail

## 边界：二次输出走另一条路

本 skill 的产物是自用笔记——忠实记录加少量标注，读者是自己。若用户要把它变成公众号文章或对外发布的观点稿，那不是「润色笔记」，是重写：结构、主体、论据都要换。

分界处有一道可数的检查：把新提纲的一级标题列出来，如果全是嘉宾的观点，说明还停在复述；至少一半是自己的判断，文章才成立。另外两条常见失误：转述时删掉限定词（「在中小团队里、多数情况下 X 更划算」写成「X 更划算」）；大段直引原话（直引只用于关键判断句，且要标时间戳）。

遇到这种需求，先说明是重写不是润色，再决定是否另起一次任务，不要在原笔记上就地把结构改出去。

## 复盘模式

当用户说“复盘这个 skill”“review this skill”或类似表达时，进入复盘模式。读取过往 `feedback-log.md`，找出出现 3 次以上的问题类型，并提出对 `SKILL.md` 或 reference 的修改建议。用户明确确认前，不要自动修改 skill 文件。

每次完整运行结束后，向 `feedback-log.md` 追加：日期、播客标识、质检失败类型、实际修复项、需要观察的反复模式。
