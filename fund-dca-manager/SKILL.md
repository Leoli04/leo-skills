# 基金定投仓位管理

## 与 fund-etf-review 的分工

| | fund-etf-review | 本 skill |
|---|---|---|
| 回答的问题 | **买什么** | **怎么买、买多少、何时卖** |
| 核心动作 | 审、比、出研报 | 算、分配、执行 |
| 典型触发 | 「评估这只基金」「有没有更便宜的替代品」 | 「本周投多少」「三只都在跌先买哪只」 |
| 输出物 | HTML 研报 + 资料库 | 终端执行表 |

两个 skill 是先后关系不是替代关系：先用 review 选定标的，再用本 skill 执行。**不要在本 skill 里做选品评估，也不要在 review 里做仓位分配。**

## 三条核心原则

**1. 统一量纲用估值历史分位，不用 PE 绝对值。**
创业板 PE 30 和沪深300 PE 13 不能比较，因为盈利结构不同。跨标的唯一可比的是「该指数 PE 在自己历史中的位置」。分位窗口必须披露（蛋卷口径自 2016-07 起，约 10.3 年，不含 2015 泡沫）。

**1.1 分位法会失效——用 PB 分位做交叉校验（脚本已默认开启）**

分位隐含「估值中枢长期稳定」的假设。中枢一旦漂移，分位就会**永远等不到低档位，或把机会读成中性**：

| 失效场景 | 机理 | 症状 |
|---|---|---|
| 无风险利率下移 | 合理 PE ≈ 1/(r−g)。10Y 国债从 3.5% 降到 1.6%，同样盈利对应的合理 PE 明显抬升 | 分位常年停在 50% 上下，S/A+ 几乎不触发 |
| 政策托底削掉左尾 | 平准资金/长钱考核让极端低点不再出现 | 历史上 5% 分位对应的价位可能永远不到 |
| 盈利周期扭曲 | PE = PB ÷ ROE。盈利下滑时 PE 被动变高，价格其实没涨 | PE 分位说「很贵」，PB 分位说「不贵」 |

**解法：PE 分位定档，PB 分位做 ±1 档校验。** 这是脚本里的默认行为（`anchors.pb_check`），不是建议。

- PB 分位比 PE 分位**低 20 个百分点以上** → 上修 1 档。差额来自 ROE：净资产没比历史贵，PE 高是盈利在下滑（周期底部形态），此时停投是错的。
- PB 分位比 PE 分位**高 20 个百分点以上** → 下修 1 档。PE 便宜但 PB 贵，是盈利虚高（周期顶部形态）。
- 差额不足 20pct → 不动。
- **基准校验是 PB 而不是 ERP**：PB 与 PE 同接口、同窗口、同量纲，不依赖外部利率；ERP 跨行业不可比（成长股盈利收益率天然低），用它统一判档会系统性压制成长与消费类。

**ERP 与回撤降级为告警，不参与定档**：

- ERP（100/PE − 10Y国债）只在页面展示，让人看到利率环境。10Y 国债值走 `anchors.bond10y` + `bond10y_asof`，超 90 天未更新要在输出里提示。
- 回撤**不单独当买入信号**：深跌既可能是机会，也可能是基本面破坏（白酒、地产链都是后者）。判断用 `anchors.dd_warn_*`，只告警「跌得多但两锚都不便宜」。

**D/E 档不再一律归零**：有了 PB 校验，被「PB 说便宜」的标的会自动上修到 C 档（0.5×），真正 0 元的只剩「PE 与 PB 双锚共振判贵」。因此**不需要额外设统一保底系数**——保底是一刀切的仁慈，PB 校验是有依据的解禁。若用户仍想要「任何情况下都保持在场」，把 `tier_rules` 里 D/E 的 `factor` 从 0 改成 0.15–0.25，并说明这是「在场维持额、不是买入信号」。

**处置纪律**：

- 分位仍是**默认口径**，不能因为担心「等不到低点」就单方面放宽阈值——放宽阈值等于放弃纪律，要用第二锚承托，不是把线挪走。
- 每次出表说明被交叉修正过的标的及理由（脚本已打 `⚑` 标记），不要静默改档。
- 手工填 `manual_percentile` 的标的没有配套 PB 分位，**不做校验**，输出里要说明这一点。

**2. 单只决定「该不该加」，账户决定「能不能加」。**
这是本 skill 与普通定投的分水岭。每只基金按分位落档，账户预算不够时按分位从低到高排——**最贵的先砍，不是平均分，也不是谁跌得狠买谁**。这个「排序」是对外可讲的判断；「具体砍到几元」只在 `--amounts` 模式下内部计算，不作为建议输出（见原则 4）。

**3. 单只限额是「可选」，默认不设。**
用户给的金额通常是**当前市值**，不是「计划投入总额度」，两者绝不能混用——把市值当额度算，会得出「已用 91%，快没钱了」这种纯属虚构的结论。所以 `pool` 默认不填＝不设上限，周投额只由档位系数与账户预算决定。只有用户明确说「这只我最多再投 X 元」时才填，填了才按 天花板 = pool × 该档 cap_ratio 截断，累计达到即停手，等估值下移到更高天花板那一档再恢复。

**4. 只给档位，不给金额。档位变了必须单独说。**
用户要的是「这只贵还是便宜、该不该加」，不是「这只投 100 还是 200」。金额属于执行决策，牵涉现金流、平台扣款设置、心理承受度，脚本没有这些信息，给出具体数字等于把不确定性包装成建议。所以：

- 默认输出**档位表**：PE / PE分位 / PB分位 / 档位 / 较上次 / 备注。终端与页面都不折算金额。
- 真要折算时加 `--amounts`，输出「理论额 / 建议额」两列，仅供内部核对预算，不写进对外结论。
- **档位变化必须显式给出**：表格有「较上次」列，另有一段汇总（`↑` = 变便宜可加码 / `↓` = 变贵收紧）。对比基线是**上一份不同 ISO 周的快照**——同周重跑往往是改了规则，把它当「档位变化」会把规则调整误报成市场变化。
- 逐只建议的措辞也守这条：写「C 档（0.5×）减速维持」，不写「投 50 元/周」；方案层只给**触发条件与相对幅度**，不给绝对金额。

## 工作流

### Step 0 先确认数据源（跨端场景必做）

持仓与配置的**真源是资料库两张数据表**，本地 `holdings.json` / `dca_plan.json` 只是渲染缓存：

| 表 | database_id | 内容 |
|---|---|---|
| 基金定投-账户 | `ISIXXhHrkmjhU4sA3kzTfN` | 账户级：总资金 / 周预算基准 / 周预算上限 |
| 基金定投-持仓 | `mCHy7qmHBeBZSaxVY8tFgi` | 一行一只：当前市值 / 成本价 / 累计投入 / 份额 / 单期定投额 / 周期周 / 平台策略 / 周投基准 / 额度上限·可选 / 估值指数 / 指数偏差说明 / 手工分位 / 备注 |

「额度上限」列留空 = 未设单只限额（默认状态）。清空该列必须用 `{"number": null}` 写入——传 `None` 会被 `validate_properties` 判为「无有效字段」，传 `{"text": ""}` 对 number 列无效，两种都会静默失败。

```bash
python sync_lib.py pull      # 表 → 本地 JSON（换设备、或用户在手机/网页改过表，先跑这个）
python sync_lib.py diff      # 本地 ↔ 表 差异，只打印不写
python sync_lib.py push      # 本地 JSON → 表，增量更新（只提交有变化的字段）
```

规则：

- **换设备第一件事是 pull**。不 pull 直接跑 `dca_weekly.py`，用的可能是另一台电脑的旧数据——这是多设备场景最容易出的错。
- 用户在网页/手机改过表，本地必须 pull 才看得到。
- 本机批量改完 JSON（回算、补市值、补成本价）要 push，否则下次 pull 会被表里的旧值覆盖回去。
- `tier_rules` / `output_dir` / `library.node_block_id` / `_legacy_dca_engine` **不进表**，只存本地 JSON，pull 不会动它们。
- push 之后必须回读核对（`query_database_record.py`）：写接口返回 `success:true` 不等于真的写进去了。
- 表里的空值（副账户当前市值/成本价缺失）是**真实缺口**，不是写入失败。要在输出里点名缺哪几只、缺哪些字段，让用户在任意一端补。
- **「累计投入」的两种口径必须分清**：表里的「累计投入」是**总累计现金投入**（用户视角）；`dca_plan.json` 的 `invested` 只是**启用台账之前的历史持仓**——`dca_weekly` 会再累加一遍台账 `actual`。`sync_lib.py` 已内置这座桥（pull 时减去台账累计、push 时加回去），**不要手工对齐，也不要把表值直接抄进 `invested`**，否则累计投入会被重复计一次。
- **「持仓成本」≠「现金投入」**：有分红的基金（如 LOF 160222）两者不等——持仓成本 = 市值 ÷ 净值 × 成本价，现金投入 = 各期实投之和。02 节算浮亏用前者、04 节与 KPI 用后者，两处必然有差额，页内已注明，对账时别当成 bug。

### Step 0b 持仓被拆分时怎么处理

同一笔钱从 A 基金转到 B 基金（例：160222 停止定投、改投 013125），**必须在表里拆成两行**，各带自己的市值/成本/份额：

- 存量那只 `base_weekly` 设 0（仍持有、不再定投），新投那只带正常基准；两者 `base_weekly` 之和才是账户周预算。
- 台账 `ledger.csv` 的 `cumulative` 列**会因拆分失真**（它按写入当时的 invested 基数算，旧行仍含拆分前金额）。渲染已改为按 `actual` 逐条累加、不读该列；**对账不要用 cumulative 列**。
- 同一 `index_code` 拆成两只后必然触发「重复暴露」告警——这是对的，不是误报：它确实让你在同一风险上有两笔钱，只是其中一笔不再长大。

### Step 1 读配置，缺项先补齐

配置在 `dca_plan.json`（模板见 `scripts/dca_plan.example.json`）。必填项：

- `accounts[]`：每个账户的 `id` / `total_capital` / `weekly_budget_base` / `weekly_budget_cap`
- `funds[]`：`code` / `name` / `account` / `index_code` / `base_weekly` / `invested` / `shares`；`pool` 可选，不填＝不设单只限额（默认）
- `funds[].reopen` 可选：`{"closed": "2026-06/07", "opened": "2026-10"}`。标记「清仓后重新开仓」——成本基准从重开日算起，浮亏不含清仓前那一段。填了页面会打「重开」徽标，并在持仓评估里提示横比会低估真实亏损

用户没给齐时**先问再算**，不要猜金额。缺 `index_code` 时查 `_可用指数代码` 对照表；表里没有的指数，改用手工填分位的降级路径。

### Step 2 跑脚本出表

```bash
python dca_weekly.py                 # 默认读同目录 dca_plan.json
python dca_weekly.py --config x.json
```

脚本自动：查蛋卷估值 → 双锚落档 → 对比上一份不同周的档位（有变化则汇总）→ 输出档位表 → 检测重复暴露 → 落盘。
加 `--amounts` 才会额外折算理论额、检查天花板、按账户分配预算；默认不碰金额。

## 结果落盘

每次运行自动写两处（`--no-save` 可关闭，只看不存）：

| 产物 | 位置 | 用途 |
|---|---|---|
| 快照 | `定投记录/YYYY-MM-DD.md` | 当日完整表 + 本周执行清单，可直接粘贴归档 |
| 台账 | `定投记录/ledger.csv` | 追加写入，**累计投入的事实源** |

台账机制：

- **按 ISO 周去重**（`iso_week` 列）。同一周内周一跑、周三再跑，不会重复记账，第二次只显示「本周已执行 X，本次不重复」。
- `actual` 列 = 实际投入，可手工修改。计划投 250 但实际只投 200 时，改这一列。
- 下次运行读 `actual` 累加；配置里的 `invested` **只填启用脚本之前的历史持仓，之后不要再改**，否则会重复计算。
- `cumulative` 列记录每次投后的累计投入，供对账。

### Step 3 逐项复核脚本结论（不可跳过）
- **分位是否最新**：看输出首行「数据日」。蛋卷通常 T+1，若用户问的是当日，需说明滞后一天。
- **重复暴露告警**：同一 index_code 被多只基金跟踪 = 同一风险押两次，必须提示用户合并或调权重。
- **天花板告警**：出现「已达该档天花板」说明该只已投满本档额度，不是故障。若整份输出里从未出现这条，先看账户头是否写着「单只不设限额」——那是默认状态，不是 bug。
- **预算不足告警**：被砍掉的标的下周可能排回前面，不是「不买」。

### Step 4 给加减仓结论（不只是念表）

按 `references/tier_rules.md` 的档位系数表解释「本周为什么是这么多」，并明确下一步触发条件：跌到哪个分位该加档、涨到哪个分位该减档。**只说金额不说触发条件等于没给结论。**

### Step 5 止盈检查（有持仓盈利时必做）

按 `references/exit_rules.md` 检查四层触发：L1 停投线、L2 移动止盈、L3 估值极值、L4 时间复核。有任一层触发或接近触发，必须主动提示，不要等用户问。

### Step 6 渲染台账并发布（用户要「看得见」时）

```bash
python publish_dca.py                # 渲染 + 上传/覆盖资料库
python publish_dca.py --no-upload    # 只渲染本地
```

产物：`定投台账_<记录日>.html`，单文件零依赖，八节结构 = KPI → 本周执行（分账户）→ **持仓评估与建议** → 估值分位标尺（含档位对照表、代理指数说明）→ 持仓与投入结构（历史成本 / 台账新增 / 市值 / 浮亏）→ 累计投入曲线 → 告警 → 历史记录。

**02 节「持仓评估与建议」**（需在配置里写 `holdings_ref` 指向持仓台账，缺该文件则本节显示提示并跳过）：

| 要素 | 做法 |
|---|---|
| 判据 | 只用两个可复算的量：**账户内权重** + **估值分位**；不做「看好/不看好」的主观评级 |
| 逐只诊断 | 权重≥15% 且分位>47% → `高位重仓`（措辞按排名区分，只有第一名能说「占比最大」）；分位>47% 且亏损≤-25% → `深亏停投`；分位≤22% 且权重<5% → `低估轻仓`；无分位/无市值 → `无分位`/`市值待补` |
| 组合三卡 | 最大风险（最大权重那只是否处在停投区）、钱没花对（账户闲置预算 vs 便宜资产的权重）、结构（停投区市值占比、前二权重、权益/债券只数） |
| 两个方案 | A 只调新钱（存量不动、随时可停）；B 再动存量（写明触发条件与幅度，如「减 1/3 ≈ X 元」「单只上限 30% 需减约 Y 元」） |
| 配色 | 浮盈亏按 A 股习惯 **红=盈利、绿=亏损**；与分位标尺的「绿=便宜」语义不同，必须在表下注明 |
| 声明 | 主题归类来自基金名称与合同基准，**不做持仓穿透**，同质化只能算到指数层面 |

**主题：三套，默认暗夜**。`night` 暗夜 / `paper` 纸感 / `plain` 简报（直角、硬横线、无卡片底色）。右上角按钮切换，选择存 `localStorage`，禁用 JS 时停在 `night`。

- 颜色一律走 CSS 变量（`--bg/--surface/--ink/--ink3/--buy/--warn/--amber/--band1..5/--tag-*/--alert-*`），**SVG 内的 fill/stroke 也用 `var()`**，换主题不重画图、不重算数据。
- 禁止在模板或内联样式里写死 `#fff`/`#1E6B4A` 之类颜色（会用 `.chartbox` 这类语义 class 承载容器样式），否则深色下会出现白块。
- 打印强制走浅色：`@media print{html[data-theme]{...}}`，选择器特异度要压过主题块。
- **无头截图验主题会失效**：内联脚本在无 `localStorage` 时强制 `set("night")`，替换 `data-theme` 属性不起作用。验 `paper`/`plain` 要另存一份、删掉 `<script>…</script>` 再截。

**03 节档位必须自解释**。只有徽标（S/A+/A/B/C/D/E）没有换算式，读者无法复核金额，也不知道阈值能不能改。固定包含：

| 要素 | 内容 |
|---|---|
| 档位对照表 | 档 / 分位区间 / 系数 / 额度占用上限（可选，未设 pool 时不生效）/ 动作 / 本周落此档（列出实际基金） |
| 生成方式 | 由 `tier_rules` 现场生成，**禁止在模板里写死行** —— 改阈值后表与金额必须一起变 |
| 必须声明的三条 | `-` = 无分位数据（是「不知道」不是「不该买」）；D/E 停投 ≠ 清仓；同一徽标可能对应两段系数（`A+` 3–6% 用 3×、6–10% 用 2×），同档两只可差一倍 |
| 金额可比性 | 周投额 = `base_weekly` × 系数，各基金 `base_weekly` 不同，**同为 B 档的两只绝对金额不可比** |
| 终端同步 | `dca_weekly.py` 在合计行下方打印档位图例，终端结论不能只有「档」列没有定义 |

分位口径必须写「2016-07 以来分位」，禁写「历史分位」（蛋卷窗口不含 2015 年泡沫）。

发布规则：
- 首次上传用 `--parent-id ujlYAui5OmAlkvfEjReBOW`（资料库「投资 / 基金和ETF」），成功后脚本自动把 `node_block_id` 回写进 `dca_plan.json` 的 `library` 段
- 之后每次运行自动用 `--node-block-id` **原地覆盖**，节点 URL 与标题不变、不产生重复条目
- 覆盖时**不要传 `--file-name`**（会改变节点标题）
- 资料库不支持删除节点，新建前必须确认 `library.node_block_id` 是否已存在

图表口径：
- 分位标尺：绿 ≤22% / 黄 22–47% / 红 >47%，与档位表的偏低/中性/停投线一一对应
- 累计曲线：起点 = 各基金 `invested` 之和（启用台账前的历史持仓），之后按每周 `actual` 累加；y 轴上界取 nice number
- 「使用率」条的红色阈值 85%，超过即触发「逼近天花板」告警

## 输出格式

1. 一句话结论：本周档位结构（几只在可加码档、几只停投），以及**档位变化**是哪几只
2. 脚本原始表（保留，便于核对）
3. 逐只说明：为什么是这一档、下一次档位切换的分位临界点（不给金额）
4. 持仓评估：最大风险（权重 × 分位同时最差的那只）、闲置预算、停投区市值占比；给「只调新钱 / 再动存量」两套动作
5. 告警汇总：重复暴露 / 天花板 / 停投 / 止盈触发

## 红线

- **不预测收益，不推荐买卖哪只基金。** 本 skill 只做预算分配与纪律执行，选品交给 fund-etf-review。
- **不擅自改用户配置里的金额。** 需要调整 `total_capital` / `base_weekly` 时先说明理由并确认。
- **不给逐只金额建议。** 输出里出现「这只投 X 元/周」就是把执行决策替用户做了，除非用户明确要求折算（`--amounts`）。档位、分位临界点、触发条件是客观量，金额不是。
- **不用「跌了多少」做加仓依据。** 触发条件是 PE 分位（定档）+ PB 分位（±1 档校验）两锚；回撤、日跌幅只作告警，不作决策变量。深跌叠加盈利下修时，回撤越深越不能加。
- **不把场外基金当 T 工具。** 场外基金按当日收盘净值成交、<7 天赎回费 1.5%，做 T 在结构上不成立（详见 `references/exit_rules.md` 末节）。
- 数据源只有蛋卷指数估值一个入口时，必须在输出里标注日期与来源；查不到分位的标的明确标 `-` 并说明原因，不要用 PE 绝对值凑数。
